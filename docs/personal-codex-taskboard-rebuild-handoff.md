## 为什么要重构

当前 Dashi Taskboard 可以作为代码基线，但不能直接作为稳定成品。已确认的问题不是单点故障，而是任务流的三个核心环节没有闭环：

1. **任务导入走了完整 AI Agent。** 简单的“导入已完成任务”被实现为启动 `codex exec`、读取工作环境、调用工具和让模型自行写入看板，而不是结构化导入或直接写入 Taskboard API。
2. **AI 对话的续聊不可恢复。** 子进程失败后，界面只显示 `Codex exited with code 1`，没有保留 stderr，用户无法定位原因或选择新会话继续。
3. **已完成任务被隐藏。** `done` 状态存在于数据中，却不在主看板中。它被收进不显眼的“其他任务”侧栏，不能承担产出复盘的作用。

## 已验证事实

- 本地数据库存在 5 个 `done` 状态任务；不是导入丢失。
- 当前源码把主看板状态硬编码为 `todo`、`in_progress`、`blocked`、`in_review`；`done`、`backlog`、`canceled` 被归到“其他任务”。
- 一次简单导入任务产生 11 次模型请求、399,664 个累计 input token，其中 335,104 为缓存命中。用户文本本身只有一条；其余来自系统/开发规则、权限和工作区信息、技能清单、历史与工具输出。
- 已完成的启动器改造只解决“独立应用启动 Codex、启动本地服务并注入左侧栏、退出时停止服务”。它不解决 Dashi 的 AI Chat 或看板信息架构缺陷。

## 产品原则（必须遵守）

1. **数据优先，不为 CRUD 调模型。** 创建、编辑、完成、归档、拖拽和状态同步必须直接调用本地 Taskboard 数据 API。
2. **完成可见且可复盘。** 默认主看板必须包含“已完成”；用户可配置是否折叠或按时间范围显示，不能藏进无标签图标。
3. **AI 是可选增强，不是数据入口。** 自然语言只能作为轻量解析/建议层；解析结果必须给用户确认，不能让通用 Coding Agent 自行修改看板。
4. **失败可诊断、可恢复。** 每个后台调用要保留受限长度的错误详情；续聊失败时应提供“显示原因 / 新会话继续 / 重试”三种明确选择。
5. **Codex 生命周期归宿清晰。** 启动器负责启动与停止，不依赖用户手工维护终端；任何非官方 DOM 注入能力都必须标记为兼容层并有降级提示。
6. **飞书后置。** 在本地任务数据、状态流转和复盘稳定前，不接飞书工作流；否则只会把不稳定状态同步到更多系统。

## 目标 MVP

- 左侧栏可打开的本地任务看板。
- 常驻列：`待办`、`处理中`、`待确认`、`已完成`；“阻塞”按需显示。
- 直接创建、编辑、完成、归档、搜索、筛选和已完成任务复盘。
- 从指定 Codex 会话/工作区结构化提取候选任务，用户确认后导入；不启动通用 Agent 来做写入。
- 任务可关联 Codex 任务/会话链接，但看板在 Codex 对话不可用时仍可独立使用。
- 受管理的启动/停止与明确的运行状态。

## 不纳入第一版

- 自动替用户执行代码任务。
- 无确认地从对话“猜测”任务并写入数据。
- 飞书双向同步、PPT/文档自动生产、多人协作权限。
- 将 DOM/CDP 注入伪装成 Codex 官方扩展能力。

## 改造任务清单

| 优先级 | 任务 | 验收标准 |
| --- | --- | --- |
| P0 | 固化基线与回归样例 | 记录当前数据库、会话失败样例、启动器行为；新增测试不依赖真实用户会话。 |
| P0 | 主看板加入常驻“已完成”列 | `done` 默认可见；完成任务能拖入、能计数、能打开详情；不再只能通过隐藏侧栏查看。 |
| P0 | 看板状态列可配置 | 用户能选择显示/隐藏 `backlog`、`blocked`、`canceled`，且配置持久化。 |
| P0 | 原生任务 CRUD 与完成闭环 | 创建、编辑、完成、恢复、归档全程不调用模型；每项在本地 API 立即可见。 |
| P1 | 替换 AI 导入为“候选任务导入器” | 仅读取用户指定的工作区/会话元数据，展示候选项和状态，再批量确认写入。 |
| P1 | AI Chat 失败诊断与恢复 | 保留安全截断后的 stderr；失败界面能区分认证、会话、配置和执行错误；支持新会话继续。 |
| P1 | 限制 AI Chat 上下文 | 移除无关技能目录、人格说明和大段工具输出；只注入明确任务、选定工作区和最小必要上下文。 |
| P1 | 明确 Codex 关联模型 | 任务记录关联原生 Codex task/thread ID、工作区和链接；不能关联时给出可理解的空状态。 |
| P1 | 启动器产品化 | 保持“打开 wrapper 即启动、退出 Codex 即停止服务”；展示健康状态、端口/注入失败原因和重启入口。 |
| P2 | 导入与审计日志 | 每次导入记录来源、候选、确认人与时间；支持撤销本次导入。 |
| P2 | 飞书工作流设计 | 只在本地模型稳定后，实现“看板已完成 → 飞书待审批/发布”的单向、可追踪同步。 |
| P2 | 打包、升级和兼容性 | 建立签名、版本号、回滚、Codex 更新兼容性检查与发布说明。 |

## 推荐实施顺序

1. P0：先修主看板、直接 CRUD、状态配置；让它先成为可靠的个人看板。
2. P1：改掉 AI 导入和续聊，不再允许 AI Chat 直接成为数据写入通道。
3. P1：把任务与 Codex 任务/会话做明确关联，并完成启动器健康状态。
4. P2：最后再评估飞书工作流；不要在基础数据模型未稳定时接双向同步。
